ClariSoft допускает один экземпляр и не передаёт следующий filename уже открытому процессу. Поэтому каждый чистый проверочный документ закрывался штатным Alt+F4 через Computer Use; после завершения своего процесса запускался оригинальный EXE со штатным аргументом имени следующего файла. Пользовательские CIFF этим путём не сохранялись. Команды открытия файла через недоступный helper-диалог не использовались как доказательство успешного открытия.

Для web-hidden-outlier первое AX-состояние было временно пустым. Повторное чтение того же живого окна подтвердило Ready/clean; исходный неуспешный результат сохранён в `initialObservation` сводки.

## Сбой Computer Use и точка остановки

На открытии `xml-web-anisotropic-yres.ciff` helper вернул ошибку:

```text
window id 18446744073386592000 was not found.
```

В том же ответе `list_windows` показывал единственное окно ClariSoft с ID `18446744073386592728` и точным путём этого CIFF. Повторная выборка свежего окна через `list_windows/get_window` вернула ту же ошибку. После неуспешного восстановления ввод в приложение остановлен. Это сбой адресации окна helper, а не доказательство ошибки загрузки CIFF.

Последние шесть файлов нельзя считать прошедшими полноценную GUI-проверку. Все шесть прошли независимые original ICiffManager filename Load, Validate, Validate2 и проверку свойств, как и предыдущие 12. GUI-диалоги Font/Pitch/XYWH в этой проверке не читались: эти параметры подтверждены оригинальными COM-компонентами и actual renderer snapshot.

В ClariSoft оставлен проверочный `xml-web-anisotropic-yres.ciff`. Автоматически вернуть исходный пользовательский документ после сбоя helper не удалось. Файл пользователя `C:/Users/GigaGeorge/Downloads/Party (Date+Par)NEW2.ciff` не менялся: SHA-256 совпал с зафиксированным после самостоятельного сохранения пользователем. Подробнее: [post-gui-hashes.json](post-gui-hashes.json). Все 18 итоговых CIFF также сохранили SHA-256.
