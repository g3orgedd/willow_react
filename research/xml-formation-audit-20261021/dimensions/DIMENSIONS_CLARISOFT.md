# Размеры SubImage в ClariSoft: проверка 21.10.2026

Проверены установленный `CLARiSOFT.exe 4.5.1.0`, `CiffMgr.dll 4.5.0.0` и `CLPrintPreview.ocx`. Источники — свежая целевая декомпиляция Ghidra, сопоставление оригинальных COM vtable с typelib и 38 вызовов оригинальной 32-битной COM-библиотеки. Исходный код Glyph не менялся. Скриншоты GUI в этой части исследования не снимались; утверждения о ветках отрисовки ниже получены из кода приложения, а не из снимков.

## Основной результат

`ImageWidth/ImageHeight` и `MaxImageWidth/MaxImageHeight` — четыре отдельные целочисленные величины. Для обычного `Units=0` (`U_HMM`) единица геометрии CIFF — 1/100 мм. Typelib также допускает `Units=1` (`U_DOTS`): в этом режиме геометрия задаётся точками, а перевод к физическому размеру зависит от разрешения. Наши COM-пробы используют обычный `Units=0`. Размеры не являются размером шрифта, коэффициентом увеличения текста или взаимозаменяемыми дублями.

- `MaxImage*` задаёт рабочее поле редактора, область проверки вписывания печатаемых полей и исходный размер листа в print preview.
- `Image*` редактор пересчитывает по правой и нижней границе печатаемых полей; эти значения также используются для команды Best Fit в print preview.
- Низкоуровневая загрузка/сериализация `CiffMgr` сама по себе не пересчитывает размеры по полям и не ограничивает `Image*` величинами `MaxImage*`.
- Важное исключение print preview: если конкретный `MaxImage*` равен **0**, для этой оси используется `Image*`. В обычной ветке фона редактора такого fallback нет.

Следовательно, фраза «предпросмотр ClariSoft берёт размер из Image» слишком общая и неверна для рабочего поля. В ClariSoft есть разные пути: редактор, подготовка печати, print preview, его Best Fit и счётчик чёрных точек.

## COM: хранение и XML

Типизированный интерфейс SubImage — `ICiffSubImage7`, IID `{9DA85228-EF2E-47C1-9E87-93D03D8CB08F}`. Смещения vtable 32-битные:

| Свойство | get / put | Реальная функция get / put |
|---|---|---|
| ImageWidth | `0x3C / 0x40` | `68112B4F / 681134EA` |
| ImageHeight | `0x44 / 0x48` | `68112949 / 681132F1` |
| MaxImageWidth | `0x5C / 0x60` | `68112C33 / 68113598` |
| MaxImageHeight | `0x64 / 0x68` | `68112BFA / 6811356E` |
| AutoSize | `0xA4 / 0xA8` | `68112477 / 68112FA7` |

Setter `ImageWidth` записывает память объекта `+0x50`, `ImageHeight` — `+0x54`; `MaxImageWidth` — другую ячейку `+0x34`. В этих setter нет пересчёта полей, clamp или требования `Image <= Max`. `AutoSize` допускает только 0 и 1, иначе возвращает `0x80070057`.

**Загрузчик `CiffMgr!68121A2A`:** сначала читает оба `Image*`, затем создаёт SubImage с этими размерами; исходные Max наследуют Image. Если `MaxImageWidth`/`MaxImageHeight` присутствуют, отдельно вызывает соответствующие setter. Отсутствующий Max поэтому получает значение Image своей оси. Отсутствие Image — не тот же случай, что нулевое значение.

**Writer `CiffMgr!6812C2CA`:** последовательно пишет `ImageWidth`, `ImageHeight`, условный `ImageRotation`, затем `MaxImageWidth`, `MaxImageHeight`, условный `AutoSize`. Все четыре размера пишутся и при нулях. Для обычной сериализации `AutoSize=0` опускается, `AutoSize=1` записывается. Ни writer, ни loader не запускают вычисление границ изображения только из-за `AutoSize=1`.

## Как редактор вычисляет Image по полям

Свежая цепочка EXE:

```text
00E2B99E -> 00E6600F -> 00EB59A2 / 00E61D8E
         -> 00E67CDB -> SubImage.put_ImageWidth / put_ImageHeight
```

`00E2B99E` получает активный SubImage/cache, создаёт прямоугольник `(0,0,0,0)`, вычисляет границы и **до каких-либо проверок Max** записывает правую/нижнюю границу в `Image*`. Проверка `AutoSize` на этом пути отсутствует. Этот метод вызывается из нескольких операций редактирования, включая `00E311EC` (изменение геометрии поля), `00E3069F`, `00E2CA77`, `00E37009`. Это не утверждение, что любой вызов низкоуровневого writer или открытие файла обязательно запускает данный путь.

`00EB59A2` читает `ICiffField.FieldDisplayed` (get `+0x24`) и возвращает `!=0`. Поэтому учитываются печатаемые поля; `Displayed=0` исключается. Все скрытые поля либо отсутствие полей дают правую/нижнюю границу 0 и, при вызове этого пути, Image 0×0.

`00E61D8E` читает целочисленные `X,Y,W,H,Orientation`. Для обычных полей:

```text
orientation 0/180:   right = X + W; bottom = Y + H
orientation 90/270:  right = X + H; bottom = Y + W
ImageWidth  = max(0, right для всех Displayed!=0)
ImageHeight = max(0, bottom для всех Displayed!=0)
```

Это размер от начала координат `(0,0)` до дальнего края. Положение самого левого поля не вычитается. Например, при X=500,W=700 получается ImageWidth=1200, а не 700. Для отрицательной дальней границы остаётся seed 0. В суммировании нет операции ceil/round: оно выполняется над уже целочисленными свойствами поля.

Специальная доказанная ветка: для `FieldType=1` (FT_BARCODE), если `BarcodeType` (get `+0xA8` в `ICiffBarcodeField` и его расширениях) находится в диапазоне 10…14, перед расчётом прямоугольника к H добавляется 1000 единиц CIFF. ASM `00E61E34` содержит `ADD [EBP+8],0x3E8`; затем применяется swap при 90/270. Typelib называет эти значения `FSTB_RSS14`, `FSTB_RSS14TRUNC`, `FSTB_RSS14STACKED`, `FSTB_RSS14STACKEDOMNI`, `FSTB_RSSLIMITED`. Это RSS-ветка, она не распространяется на обычный DataMatrix.

`00E2B99E` имеет отдельную ветку для printer type `Line` (`00E66FDE`): если содержимое шире Max, расширяет MaxWidth и обновляет рабочий размер view; ветка не является общим правилом для всех принтеров. Путь с превышением только высоты обновляет размеры view, но не содержит симметричного `put_MaxImageHeight` в данной функции. Нельзя заменять это общим правилом «Max всегда равен габаритам содержимого».

## Проверка вписывания в Max

`EXE!00EB1A01`, вызванный из `00E33E72`, читает **MaxWidth/MaxHeight**. Для `Displayed!=0` переводит Max, X,Y,W,H в точки принтера через `00EAEAE0` с X/Y resolution из capabilities. При 90/270 меняет местами W/H и проверяет `X>=0`, `Y>=0`, `X+rotatedW<=MaxW`, `Y+rotatedH<=MaxH`. Имеются дополнительные условия режима редактора и особых возможностей принтера; универсального pixel-exact clamp не утверждается.

При `Displayed=0` эта проверка границ пропускается. Поэтому скрытые источники тегов могут находиться вне печатаемой области и при этом не увеличивать Image. Важно отличать такую проверку от отсечения нарисованных пикселей: она управляет признанием проблемного поля, а не сама является `SetClipRgn`.

## Рабочее поле и сетка редактора

`EXE!00E2D699`, ветка `param_2==0`:

1. Выбирает активный SubImage.
2. Читает `get_MaxImageWidth +0x5C`, `get_MaxImageHeight +0x64`.
3. Создаёт прямоугольник `(0,0,MaxW,MaxH)`, переводит в координаты view через `00E3E6ED`, добавляет 1 к правой/нижней границе для линии рамки.
4. Передаёт прямоугольник в фон/лист `00E2DE4E` и сетку `00E33906`.

`00E33899` заливает общий GetClipBox DC фоном рабочей области. `00E33906` ограничивает рисование сетки прямоугольником листа и доступной областью DC. Сам редактор также обходит cached fields для рисования: этот факт не даёт основания обещать, что текст за Max просто отрезается; проблемные/скрытые поля имеют специальные состояния отображения.

**Следствие из кода:** при фиксированном Max изменение одних Image не меняет размер этого листа и сетки и не является операцией изменения шрифта/масштаба поля. Изменение Max меняет лист и область допустимого размещения. Нулевой Max в этой ветке не заменяется Image.

Надпись «100%» не достаточна для сравнения экранных пикселей с Glyph. Например, `00E867D5` использует `GetDeviceCaps(LOGPIXELSX/LOGPIXELSY)`, resolution capabilities и `SetWindowExtEx/SetViewportExtEx`; физический экранный размер зависит от пути отрисовки/DC. Из этого не следует универсальное значение CSS px/mm для ClariSoft.

## Print preview: разные потребители размеров

Исследован отдельный `CLPrintPreview.ocx`; typelib сохранён рядом с этим отчётом в `CLPrintPreview.ocx.typelib.json`, live-адреса оригинального интерфейса — `preview-live-vtable.json`. Интерфейс `ICLPrintPreview7` IID `{6BC4AC39-AAA0-4079-9D52-DB3670806ECE}`.

`EXE!00E98F3D` передаёт документ, printer capabilities, SubImage, coder, format и пути шрифтов/перевода символов в `Preview2 +0x6C`. Реальный вход OCX — `3F417268`, далее `3F4175DB` и `3F4169EF`.

Последняя функция явно создаёт отдельный conversion request с `ConversionRequestSource="Print Preview"` и включает шаги `CS Cull`, `CS Resolution Adjust`, `CS Font Convert`, `CS Resolve Field Width`, `CS Position`, `CS Tag` и другие. Поэтому print preview не сводится к повторному рисованию исходного XML редактором; сериализованные W/H и размеры до/после conversion могут различаться.

| Действие print preview | Что читает | Адрес / эффект |
|---|---|---|
| Размер листа одного SubImage | MaxW/H, только при **0** fallback на Image соответствующей оси | `3F412CE9`; затем resolution/capabilities и extents `+1B0/+1B4/+1B8/+1BC`, фон/рамка через `3F412846` |
| Составное изображение (stitched) | То же правило для каждого SubImage | `3F413A63`; общая ширина max, высота сумма |
| Best Fit | ImageW/H | `3F418143`, get `+3C/+44`; считает коэффициент помещения содержимого в доступное окно; для stitched отдельная ветка |
| CountBlackDots, возвращаемые размеры | MaxW/H | `3F41595C`, get `+5C/+64`; размер растровой области также использует ранее вычисленные extents |
| Текст “Image Size …mm” | Результат CountBlackDots | `EXE!00E98D5F`, деление на единицы/мм |

Ветвь единиц документа `+0x130` и возможности принтера влияют на пересчёт/ограничение print-preview extent. `3F412CE9` читает ограничения из printer/format capabilities; наличие особого capability `+0x41C` меняет правило превышения для одной из веток. Для всех printer families универсальная формула одного clamp не восстановлена.

**Практическое следствие:** для Max=2000×3000 и Image=600×700 исходный лист имеет 20×30 мм, но Best Fit ориентируется на 6×7 мм. При изменении только Image Best Fit может дать другое визуальное увеличение при неизменном размере листа. При Max=0 используется Image для этой оси print-preview листа. Прямые снимки одного и того же zoom/window/device в этой части не выполнялись; эффект следует из свежей цепочки getter → вычисление zoom/extent.

Полный путь аппаратного clipping пикселей каждого вида полей после conversion не объявляется восстановленным. Доказаны выбор размеров листа, проверка размещения, агрегирование, Best Fit, счётчик и отдельная подготовка печати.

## Сопоставление с текущим Glyph (данные отдельной проверки)

Отдельный audit Glyph выполнил production-harness probes, сохранённые в `../glyph/dimension-probes.json`. Следующие отличия подтверждаются сопоставлением с кодом ClariSoft выше:

| Сценарий | ClariSoft | Glyph 2.3.0, production harness |
|---|---|---|
| Нормальные Max > 0 | Лист редактора берёт Max | Canvas берёт Max; поведение согласовано |
| Нет Max | Loader наследует Image и writer пишет Max | Также использует Image и добавляет Max |
| Нет Image | Оригинальный loader отклоняет | Может открыть workspace из printer profile; сохранение с нулевым Image отклоняется |
| Последнее печатаемое поле удалено / все скрыты | При выполнении агрегирования Image становится 0×0 | Сохраняет старый Image как fallback |
| AutoSize 1, простая load/save | Нет автоматического пересчёта | Флаг сохраняется; сам по себе не меняет workspace |
| Печатное поле изменено | App aggregate вычисляет max правых/нижних краёв Displayed!=0 | Основной принцип совпадает; точные printer conversions требуют отдельных сценариев |
| Поле неизменно лежит вне Max | COM writer способен сохранить; это не означает, что UI считает его корректным | Неизменённое такое поле допускается; изменение с выходом за Max отклоняется |
| Явный нулевой Max | Editor использует 0; print preview fallback Image по оси | Нужно проверять отдельно; нельзя переносить общий missing-Max fallback на явный 0 |

По этой части не предлагается менять все четыре числа на одинаковые: это уничтожило бы различие между рабочим полем и занимаемым изображением и изменило бы поведение Best Fit/печати.
