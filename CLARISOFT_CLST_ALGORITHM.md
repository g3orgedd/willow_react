# Алгоритм ClStVersionInfo в Clarisoft и сравнение с Glyph

Исправления production от 21 октября описаны в [отчёте о реализации](research/clst/implementation-2026-10-21/README.md). Таблица сравнения ниже фиксирует состояние Glyph до этих исправлений.

Проверено 20 октября 2026 года для установленной `CiffMgr.dll` версии `4.5.0.0`.

**CONFIRMED:** преобразование строк `E` в текущем Glyph соответствует исходному машинному коду этой DLL для штатных ключей ClSt. Полный алгоритм сохранения Glyph отличается от Clarisoft: выбирает первое поддерживаемое поле, использует собственный resolver значений, исключает данные последующих SubImage и подставляет старое значение или константу для пустого документа. Поэтому совпадение самого преобразования ещё не означает совпадения генераторов.

Ниже приведён алгоритм установленной Clarisoft, включая преобразование `E`, затем различия текущего кода Glyph. Исследована часть программы, которая формирует ClStVersionInfo, и связанные COM-интерфейсы. Исходники приложения Glyph не изменялись.

## Входные данные генератора

`6811861C` формирует токен. `68118879` получает три количества:

```text
D = количество DateOffset документа
S = количество SubImage
F = суммарное количество Field во всех SubImage

counts6 = decimal2(min(D, 99))
        + decimal2(min(S, 99))
        + decimal2(min(F, 99))
```

Например, `D=0, S=1, F=3` даёт `000103`. В алгоритме выбора используется полное `F`, а не ограниченное до 99 значение.

Поля перечисляются в текущем порядке COM-коллекций: сначала SubImage, затем Field внутри каждого SubImage. Это порядок модели в момент генерации. Предшествующие conversion-этапы способны изменить коллекцию; по координатам генератор ClSt самостоятельно поля не сортирует.

Источник выбранного текста — свойство **`ICiffField.CalculatedData`**, слот vtable `+0x98`, IID `{B2A04AE2-991E-444D-B6EB-C9171E8AB98F}`. Его читает `68118A19`. `TagData` — имя ключа преобразования, а не отдельный неизвестный XML-тег.

Генератор сам не рассчитывает дату, время или DataMatrix. Он читает уже подготовленное CalculatedData. Нужные Resolve/UpdateData выполняются до его вызова. Чтение происходит до фильтрации управляющих символов при записи XML CalcData. Поэтому сохранённый XML CalcData не всегда является точной копией входа токена.

## Случайная маска выбора

`68118E73` при каждом вызове заново выполняет:

```text
randomIndex(bound):
    tick = GetTickCount()
    srand(tick)
    return rand() % bound
```

Для используемого шага MSVCRT это эквивалентно:

```text
s = (tick * 0x343FD + 0x269EC3) mod 2^32
r = (s >> 16) & 0x7FFF
return r % bound
```

Построение маски:

```text
mask = 0
if F > 0:
    attempts = 1 + randomIndex(min(F, 3))
    repeat attempts times:
        bitIndex = randomIndex(min(F, 32))
        mask = uint32(mask OR (1 << bitIndex))

maskHex = uppercaseHex8(mask)
```

Выбор ограничен первыми 32 полями сквозной последовательности. Повторные индексы допускаются: три попытки могут оставить только один установленный бит. Все поля входят в `F`, в том числе скрытые и графические; native-генератор не ищет сначала тип, который поддерживает Glyph.

Это не независимые равномерные вызовы современного RNG: каждый вызов reseed выполняется заново, а несколько вызовов могут получить один tick. Для точного воспроизведения конкретного сохранения нужны фактические tick либо фактически выбранная маска. Одинаковый шаблон при разных сохранениях может получить разные токены.

## Основной алгоритм формирования

Здесь `E(text, key)` — описанное далее преобразование с seed `0x26E20115` и флагом подключения битов ключа `0`.

```text
generateClSt(document, includeFileMetadata):
    D, S, F = inspectCollections(document)
    counts6 = decimal2(min(D,99)) + decimal2(min(S,99)) + decimal2(min(F,99))

    fields = flattenSubImagesAndFieldsInCurrentCollectionOrder(document)
    mask = 0
    selectedBlock = ""

    if F > 0:
        attempts = 1 + randomIndex(min(F,3))
        repeat attempts times:
            mask = uint32(mask OR (1 << randomIndex(min(F,32))))

        selectedText = ""
        for i = 0 .. min(F,32)-1:
            if bit(mask,i) == 1:
                selectedText += fields[i].CalculatedData

        selectedText = first20UTF16Units(selectedText)
        selectedBlock = E(selectedText, "TagData")

    maskHex = uppercaseHex8(mask)
    inner = E(maskHex, counts6) + selectedBlock

    if includeFileMetadata:
        fileText = filenameMetadata(document.FileName)
        fileBlock = E(fileText, "TagData")
        lengthText = lowercaseHex8(UTF16Length(fileBlock))
        inner = E(lengthText, counts6) + fileBlock + inner

    result = E(inner, "TpyRcNeyeK")
    document.VersionInfo = result
    return result
```

`6811823C` выполняет конкатенацию BSTR через `VarBstrCat`. Усечение в `68118A19` происходит **после** конкатенации выбранных значений. Длина измеряется в 16-битных единицах UTF16; суррогатная пара может оказаться разрезанной. Пустой BSTR или native null-результат пустого преобразования в формулах рассматривается как пустая строка.

Для основного режима:

```text
ClStVersionInfo = E(E(maskHex, counts6) + E(selectedText, "TagData"), "TpyRcNeyeK")
length = 72 + 9 * UTF16Length(selectedText)
```

Длина составляет от 72 до 252 символов. Для `F=0` блок выбранного текста пропускается, но остальной алгоритм продолжает работать.

### Пустой документ

Особой неизвестной ветки пустого шаблона в этом генераторе нет. В основном режиме `F=0` даёт маску `00000000`, пустой selectedBlock и 72-символьный результат:

```text
PyOA!LMe37jF5gGD_OEeQJPAIR3Et2HVCOk4RKDB93Hl9AjBVgIOzL2x64vRUW8LPDPLLM!A
```

Он получен заново оригинальным COM-генератором как без SubImage, так и с одним пустым SubImage. Совпадение этих двух вариантов объясняется свойствами ключа counts6, описанными ниже. Это контрольный результат алгоритма этой сборки, а не предлагаемая замена генератора константой. Включённые optional-метаданные оборачивают и пустой основной блок.

## Точное преобразование E

`68117D03` — encrypt, `68117C0A` — decrypt. Каждый отдельный вызов `E` заново инициализирует сеть и состояние; состояние между блоками маски, данных, имени и финального токена не переносится.

Конструкторы `6810A989` и `6810A9B5` задают:

| Параметр | Значение |
| --- | --- |
| Seed сети | `0x26E20115` |
| Число узлов | 25 |
| Число входов каждого узла | 10 |
| Общая Boolean-таблица | 1024 элемента |
| Разрядность слова | 16 бит |
| Алфавит | `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz!_` |
| Ключ данных и имени | `TagData`, длина 7 |
| Финальный ключ | `TpyRcNeyeK`, длина 10 |

Финальный ключ конструктор получает изменением отдельных символов строки `spaRtNoyAK`. Для ClSt во всех разобранных вызовах используется флаг `0`.

### Инициализация сети

В native ключ копируется до первого NUL и максимум до 14 UTF16 единиц. Ни один штатный ключ ClSt это ограничение не превышает. Псевдокод ниже описывает непустые штатные ключи.

```text
E(text, key):
    key = first14UTF16Units(prefixBeforeNUL(key))
    rngState = 0x26E20115

    rand15():
        rngState = (rngState * 0x41C64E6D + 0x3039) mod 2^32
        return (rngState >> 16) & 0x7FFF

    for i = 0 .. 1023:
        table[i] = rand15() & 1

    for node = 0 .. 24:
        selectors[node] = []
        while length(selectors[node]) < 10:
            candidate = rand15() % 41
            if candidate not in selectors[node]:
                append candidate to selectors[node]

    outputs[0..24] = 0
    state = 0
    keyIndex = 0
```

Сначала целиком строится таблица, затем selectors узлов в порядке 0–24. Отклонённый повтор candidate тоже расходует шаг RNG. Индексы уникальны внутри одного узла, но могут повторяться у разных узлов. Умножение следует выполнять с точной арифметикой по модулю 2^32, например через `Math.imul` в JavaScript.

Этот LCG отличается от MSVCRT RNG, выбирающего поля. Смешивать два генератора нельзя.

### Обновление состояния

```text
update(plainWord):
    inputs[0..24] = previous outputs[0..24]

    for i = 0 .. 15:
        inputs[25+i] = (plainWord >> i) & 1
        inputs[41+i] = (key[keyIndex] >> i) & 1
    keyIndex = (keyIndex + 1) mod UTF16Length(key)

    for node = 0 .. 24:
        tableIndex = 0
        for j = 0 .. 9:
            tableIndex += inputs[selectors[node][j]] << j
        newOutputs[node] = table[tableIndex]

    outputs = newOutputs
    state = sum(outputs[i] << i for i = 0 .. 15)
```

Биты раскладываются младшими вперёд. Все 25 новых outputs вычисляются из одного старого набора inputs, одновременно с точки зрения алгоритма. Первые 16 outputs образуют 16-битное состояние, остальные девять также участвуют в следующем обновлении сети.

До обработки текста выполняется прогрев:

```text
repeat UTF16Length(key) times:
    update(0)
```

### Шифрование слова и кодирование

```text
result = ""
for plainWord in UTF16Units(text):
    cipherWord = (state XOR plainWord) & 0xFFFF
    update(plainWord)

    result += alphabet[(cipherWord >> 11) & 31]
    result += alphabet[(cipherWord >> 5) & 63]
    result += alphabet[cipherWord & 31]
return result
```

Сеть обновляется **plaintext**, а XOR использует состояние до этого обновления. Каждое 16-битное слово даёт три символа в раскладке 5/6/5 бит. Это конкретное кодирование DLL; подстановка стандартного Base64 не воспроизводит результат.

При расшифровке тройка символов собирается обратно:

```text
cipherWord = (index(a) << 11) | (index(b) << 5) | index(c)
plainWord = state XOR cipherWord
update(plainWord)
```

Длина входного текста в native определяется через `SysStringLen`: текст самого `E` может содержать NUL и продолжение после него. Это отличается от ограничений копирования ключа. Отдельная COM-проба установки CalculatedData со встроенным NUL уже на чтении свойства вернула `AB`; её нельзя считать проверкой передачи `AB\0CD` целиком через COM. Такой вход самого преобразования проверен отдельно машинным oracle.

### Почему содержимое counts6 не меняет преобразование

При флаге `0` selectors выбираются только среди входов `0..40`: старые outputs и биты plaintext. Биты keyWord лежат в `41..56` и сеть их не выбирает. Поэтому значение ключа влияет только эффективной длиной и числом прогревочных шагов.

Следовательно:

```text
E(maskHex, "000101") == E(maskHex, "999999")
```

Это поведение оригинальной DLL. Само изменение D, S или F не обязано менять токен, если маска, выбранные данные и optional-режим остались теми же. Например, добавление невыбранного поля в конец документа может оставить токен неизменным. Генератор не формирует обычный хеш всего XML.

## Optional блок имени файла

Флаг `[generator+0xC]` по умолчанию равен нулю. `681182FA` используется только при включённом флаге, независимо от количества полей.

```text
filenameMetadata(sourcePath):
    name, extension = WindowsSplitPath(sourcePath).filenameAndExtension
    if extension == ".new":
        name, extension = WindowsSplitPath(name).filenameAndExtension
    return first100UTF16Units(name) + extension
```

Диск и каталог не входят в строку. Сравнение `.new` регистрозависимое. Ограничивается только name, расширение сохраняется:

| Исходный путь | Вход fileBlock |
| --- | --- |
| `C:\labels\Report.ciff` | `Report.ciff` |
| `D:\other\Report.ciff` | `Report.ciff` |
| `Report.ciff.new` | `Report.ciff` |
| `Report.ciff.NEW` | `Report.ciff.NEW` |
| `Report.new` | `Report` |

Затем перед обычным inner добавляются два блока:

```text
fileBlock = E(filenameMetadata(sourcePath), "TagData")
lengthText = lowercaseHex8(length(fileBlock))
inner = E(lengthText, counts6) + fileBlock + normalInner
result = E(inner, "TpyRcNeyeK")
```

Длина fileBlock измеряется в символах закодированной строки, не в байтах исходного имени. Для длины выбранных данных P и длины подготовленного имени Q итоговая длина составляет `144 + 9*(P+Q)`.

Валидатор `68118E92` распознаёт такой envelope в загруженном токене через `68118C55` и записывает результат в `[generator+0xC]`. Он проверяет длину блока, расшифровывает имя, сравнивает basename по первым 100 UTF16 единицам и расширение без учёта регистра, требует текущее расширение `.ciff`. Это поддерживаемый режим существующего токена. Утверждение, что каждое новое сохранение Clarisoft обязательно содержит имя файла, не подтверждено.

Подробные условия и адреса находятся в [optional/findings.md](research/clst/optional/findings.md). Native-буферы filename и extension в splitpath рассчитаны каждый на 255 UTF16 единиц плюс терминатор. Восстановленный reference отвергает превышение этих ёмкостей; аварийные CRT-ветви переполнения не воспроизводятся.

## Сравнение текущего Glyph с Clarisoft

| Этап | Clarisoft | Текущий Glyph | Практическое отличие |
| --- | --- | --- | --- |
| Преобразование E | Сеть, seed, XOR, кодирование 5/6/5 | Соответствует для штатных ключей | Ядро преобразования уже восстановлено |
| counts6 и maskHex | Три количества с пределом 99, маска uppercase hex8 | Те же форматы | Совпадает |
| Выбор поля | 1–3 случайные попытки среди первых 32 | Первое поле с разрешаемым значением, один бит | Весь генератор не повторяет native selection |
| Значение поля | Готовое CalculatedData любого выбранного типа | Свои форматтеры и resolver по fldType | Совпадение зависит от эквивалентности расчёта данных |
| Скрытые и графические поля | Участвуют в общей последовательности | Скрытость сама по себе не исключает поле; resolver пропускает неподдерживаемые типы | Возможны другая маска и другие данные |
| Последующие SubImage | Их поля участвуют в сквозном обходе | Save adapter подменяет их на UnsupportedClStField | Runtime-данные этих полей недоступны генератору Glyph |
| Обрезка payload | После конкатенации до 20 UTF16 единиц | Так же | Совпадает |
| Пустой документ | Маска 0, обычная сборка, 72 символа | Генератор возвращает null; save использует старое значение или константу | Пустой путь не воспроизведён |
| Optional имя | Условный envelope из двух блоков | Не собирается | Режим существующего токена не воспроизводится при регенерации |
| Ограничения ключа | До NUL, максимум 14 UTF16 единиц | Вся JS-строка | Отличается общий класс; ключи ClSt длиной 6, 7 и 10 не затронуты |
| Пригодность загруженного токена | Native расшифровка и проверки | Проверка непустоты, пробелов и обратной косой черты | isUsableClStVersionInfo не является native-валидатором |

Выбор одного бита сам по себе допустим и для native. Подтверждённое различие — политика выбора и покрытие данных; из него не следует автоматически, что любой токен Glyph с одним битом будет отвергнут принтером.

### Места в исходниках Glyph

- [encryption.js](public/modules/clst/encryption.js), строки 1–108: преобразование E. Конструктор и прогрев — 10–26; сеть — 33–46; обновление — 48–78; XOR — 80–85; кодирование — 87–91; цикл текста — 93–100; обёртка — 103–105.
- [tag-data.js](public/modules/clst/tag-data.js), строки 69–108: resolver по типу; 160–185: первое поддерживаемое поле; 189–203: конкатенация и усечение. При рекурсивной ссылке DataMatrix строки 52–58 берут значение источника целиком.
- [version-info.js](public/modules/clst/version-info.js), строки 47–51: отказ генерации для нуля полей. Комментарий про неизвестную special empty branch устарел. Строки 56–63 формируют только основной непустой путь.
- [60-history-save.js](public/modules/60-history-save.js), строки 634–665: подготовка модели; 651–656: заглушки следующих SubImage; 676–685: сохранение пустого документа через fallback; 698–711: fallback при отсутствии разрешаемых данных.
- [01-ciff-compatibility.js](public/modules/01-ciff-compatibility.js), строки 1–3: константа; 18–20: упрощённая проверка пригодности; 23–30: выбор старого значения или константы.

`EMPTY_TEMPLATE_CLST_VERSION_INFO` — 252-символьный токен из непустого `tests/fixtures/clarisoft/Clarisoft_test_1.ciff`. Он декодируется в маску `00000001` и payload `~1010000000000000021`. Это не результат native-генерации для пустого документа. Предыдущий разбор корпуса сохранён в [fixture-analysis.json](research/clst/fixture-analysis.json).

Resolver Glyph требует отдельной проверки для runtime-дат, времени, локалей, padding, источников и счётчиков. Например, native поддерживает частичную ссылку `SrcField ABCDE`, `StartChar=1`, `NoOfChars=3`, дающую `BCD`, и дополнение нестатического FixedLen `abc` до `000abc`. Текущий DataMatrix parser сохраняет ограниченный набор параметров сегмента, а resolver подставляет всё значение источника. Подтверждения native-правил: [FIELD_FORMATION_SPEC.md](research/ciff-fields/FIELD_FORMATION_SPEC.md), разделы о разрешении данных и месте ClSt в цикле сохранения.

## Результаты свежих сравнений

Полный оригинальный COM-генератор совпал с восстановленной сборкой во всех **13 из 13** случаев. Для сравнения расшифровывалась фактическая native-маска и передавалась в reference вместе со снимком исходного CalculatedData. Таким способом проверяется сборка при фактическом выборе; распределение RNG этим не измеряется.

Некоторые фактические результаты этого запуска:

| Сценарий | Маска | Payload | Длина токена |
| --- | --- | --- | --- |
| Без SubImage | `00000000` | пусто | 72 |
| Пустой SubImage | `00000000` | пусто | 72 |
| Одно поле alpha | `00000001` | `alpha` | 117 |
| Три поля alpha beta gamma | `00000004` | `gamma` | 117 |
| Поле только во втором SubImage | `00000001` | `SECOND-IMAGE` | 180 |
| Два SubImage по два поля | `00000008` | `I2-B` | 108 |
| 33 поля | `00000008` | `FieldValue03` | 180 |
| Длинный текст | `00000001` | `12345678901234567890` | 252 |
| Управляющие символы | `00000001` | `AB\u0001CD\u001dEF` | 144 |
| Скрытое поле | `00000001` | `HIDDEN` | 126 |

В пробе управляющих символов токен совпал с исходным COM CalculatedData и **не совпал** со строкой, собранной из очищенного XML CalcData. В Unicode-пробе native оставил первые 19 цифр и одиночный high surrogate `D83D`, подтвердив усечение по UTF16 единицам.

Контролируемые вызовы production-генератора выполнялись в Node VM с инъекцией `resolveTagData` и явными значениями полей. Пустой save проверялся через существующий Node harness с заглушками DOM/UI и отключёнными проверками геометрии. Эти сравнения проверяют политику генерации и fallback; они не проверяют интерфейс приложения или эквивалентность native resolver.

Контролируемое сравнение с production Glyph дополнительно показывает:

- Для одного `alpha` без optional-метаданных основной токен совпадает, длина 117.
- При `alpha,beta,gamma` Glyph выбирает mask1 и `alpha`. Native в свежем COM-запуске выбрал mask4 и `gamma`: даже равная длина 117 не означает равенство токенов. Допустимая reference-маска 6 даёт `betagamma` и длину 153.
- Для пустого документа генератор Glyph возвращает null; действующий save fallback может выдать 252-символьную константу вместо native 72.
- Добавление невыбранного поля в конец меняет counts6 с `000101` на `000102`, но при той же маске и данных токен сохраняется.
- Optional-режим для `alpha` и `Report.ciff.new` даёт 288 символов; основной режим Glyph даёт 117. Это сравнение с принудительно включённым reference-режимом, а не утверждение о включении optional при каждом сохранении через UI.

Отдельные исполнения оригинального x86-преобразования подтвердили **200 из 200** дополнительных обычных примеров и три прежних контрольных вектора. Обёртка с native-ограничениями ключей совпала в **204 из 204** случаев. Два отличия общего production-класса относятся к длинному ключу и ключу с NUL. Проверены также **16 из 16** основных композиций, **8 из 8** optional-композиций и **31 из 31** разборов имени файла.

Три существующих набора Node-тестов проходят **41 из 41** проверок. Часть тестов закрепляет текущие упрощения, включая константу для пустого документа; поэтому этот результат не доказывает полную эквивалентность алгоритму Clarisoft.
